# Windows ログイン画面への導入

開発用の V2 Credential Provider と設定アプリを実装済み。実際の登録・ログイン試験には、所有者が設定アプリで資格情報とカードを登録する必要がある。管理者権限が必要。Windows の既存のパスワード／Windows Hello Provider は変更しない。

## 手順

1. `scripts/Build-LogonBundle.ps1` で一式をビルドする。出力は `artifacts/MynaAuth-Logon/`。
2. そのフォルダーの `MynaAuth.Setup.exe` を起動し、管理者権限の確認に応じる。
3. 「Windows の確認」で自動入力された Windows アカウントを確認し、そのユーザーの Windows パスワードを入力する。ローカルユーザーは `PC名\ユーザー名`、Microsoft アカウントはメールアドレスを指定する。メールアドレスに `MicrosoftAccount\` を付ける必要はない。Windows Hello の PIN は Windows パスワードの代用にはならない。この確認が成功するまでカードの PIN は求めない。
4. 「カードの登録」で登録するカード／スマホの利用者証明用 PIN を入力し、「登録を開始 → かざす」を押してから媒体をかざす。両方使う場合はそれぞれ登録する。入力値はチャット・コマンド引数・設定サンプルへ記載しない。
5. 「登録完了」を押して、「ログイン画面へ追加」で内容を確認して追加する。ここで初めて Program Files への配置と COM／Credential Provider の登録を行う。
6. 作業を保存後、Windows のサインイン オプションで「マイナンバーカードによるログイン」（ID カード風のフォントアイコン）を選び、対象媒体の PIN を 4 桁入力してかざす。4桁の数字が揃うと自動で読み取りを開始し、Enter は不要。同じ入力通知では再送せず、失敗時に PIN を自動再試行しない。自動の再起動・ロック・サインアウトは行わない。

Windows アカウントのパスワード変更後は、標準の方法でサインインし、設定アプリから Windows パスワードを登録し直す。Windows パスワードを使えない構成や空パスワードは対象外。ローカル／Microsoft アカウントに対応し、AD／Entra アカウントを対象とした導入はまだ提供しない。ローカルアカウントにはローカル向けの資格情報形式を使用し、オンライン ID 用の形式を強制しない。

失敗時は、画面に表示された段階とエラー番号を確認する。設定アプリの `setup-diagnostics.log` は、最後の失敗の日時・段階・数値コードのみを記録する。PIN・パスワード・メールアドレス・証明書・SID・例外本文は記録しない。手順式の改訂版は `scripts/Build-LogonBundle.ps1 -BundleName MynaAuth-Logon-v2` で別フォルダーへビルドできる。

## 保護方式

- カード／スマホの PIN は保存しない。認証1回ごとに照合し、失敗後に別方式へ切り替えたり PIN を自動再送したりしない。
- Windows パスワードは、所有者が許可した保存方式として Windows DPAPI のマシン保護で暗号化する。暗号化データは HKLM の MynaAuth 専用キーに格納し、SYSTEM と管理者だけがアクセスできる ACL を適用する。DPAPI のマシン保護だけでは他のユーザーとのアクセス境界にならないため、この ACL が必要。
- 保存する登録情報は対象の Windows SID、資格情報のアカウント名、許可する公開鍵の SHA-256 識別値。個人の証明書全体は保存しない。これらの対応表も個人に結びつくため、リポジトリや診断ログには書かない。
- ネイティブ DLL はログイン画面の入力と Windows への資格情報引き渡しを担当する。カード処理と暗号化データの復号は専用の .NET プロセスで行い、登録した公開鍵による署名検証に成功してから復号する。
- 専用プロセスは SYSTEM での実行を必須とし、Windows パスワードを平文でプロセス間送信しない。Windows が扱えるセッション保護済みの資格情報バッファだけを、継承した非公開の匿名パイプで親に返す。PIN も引数ではなく匿名パイプ経由。
- 子プロセスに継承できるハンドルは専用パイプに限定する。親が終了した場合はジョブによって子も終了し、処理は最大約65秒で打ち切る。通常ログオンでホストが Connect を呼ばない場合は GetSerialization 内でこの時間上限付き処理を行うため、認証中に画面応答が遅れることがある。
- 導入先は `%ProgramFiles%\MynaAuthSignIn`。標準ユーザーは読み取り・実行だけとし、管理者／SYSTEM がファイルを管理する。バンドル内のファイルハッシュを配置前後に確認する。ハッシュマニフェストは転送・配置不整合の検出用で、発行元の署名ではない。
- 復号できる権限を持つ管理者や SYSTEM の侵害までは防げない。Windows の標準ログイン方式を残すため、カード方式を強制する製品でもない。オンライン失効確認はプロトタイプ同様に未実装。

## 削除・復旧

導入済み環境では設定アプリが既存登録を検出して更新処理を実行する。手動で更新するときは、管理者権限の64-bit Windows PowerShell から `scripts/Update-LogonProvider.ps1 -BundlePath <ビルド済みフォルダー>` を実行する。ファイルを新しい保護フォルダーに配置し、検証後に MynaAuth の COM 登録先だけを切り替える。登録済みの媒体と暗号化パスワードは維持する。読み込み中の旧 DLL は上書き・削除しない。表示が旧版のままの場合は、作業保存後に Windows を再起動する。

標準のパスワード／Windows Hello または復旧管理者でサインインし、管理者権限の64-bit Windows PowerShell で実行する。

```powershell
& "$env:ProgramFiles\MynaAuthSignIn\Uninstall-LogonProvider.ps1"
```

MynaAuth の登録だけを削除する。Windows 標準 Provider、復旧アカウント、他の Provider は変更しない。DLL が LogonUI からロード中の場合があるためファイルは残す。登録済み公開鍵と暗号化 Windows パスワードも削除する場合は `-RemoveEnrollment` を付ける。

設定アプリが使えない場合も、管理者権限で次の2キーだけを削除すれば MynaAuth の読み込みを停止できる。

```powershell
Remove-Item -LiteralPath 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers\{37167329-B6D8-4379-90A9-0D350F82F31A}' -Recurse -Force
Remove-Item -LiteralPath 'HKLM:\SOFTWARE\Classes\CLSID\{37167329-B6D8-4379-90A9-0D350F82F31A}' -Recurse -Force
```

## 検証状況

カード認証の既存検証に加え、合成データで登録鍵の一致・不一致、DPAPI 暗号化、Windows 向けの保護された資格情報の組み立て、暗号文改ざんの拒否を確認。ネイティブ DLL の COM 作成・フィールド列挙、未認証／不正 PIN 時にシリアライズ済み資格情報を返さないこと、PIN 消去を確認。通常ユーザーから専用プロセスを呼んでも資格情報が返らないことと、設定画面の復旧確認・登録前の導入拒否も確認した。

これらは実際のログイン画面でのエンドツーエンド試験の代わりにはならない。SYSTEM 下でのカードリーダー・JPKI の挙動、Microsoft アカウントの実ログオン、再起動後のロック解除は、所有者の登録後に確認が必要。ビルド済みであることを導入・実ログオンの成功とは扱わない。
