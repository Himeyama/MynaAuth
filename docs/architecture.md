# 実装方針と調査

調査日: 2026-11-03。公式資料を優先。実装済みのプロトタイプと、今後の Windows 統合の計画を記す。

## デスクトップのプロトタイプ

WPF の独立アプリ。Windows ログオンへの登録は行わない。実カード認証、模擬認証、提示検出の3モードを持つ。提示検出モードは SCardGetStatusChangeW によるカード存在の変化だけを見る。実カードモードは JPKI の利用者証明用 PKCS#11 ライブラリを使用する。

実カードモードだけ実際の PIN を入力する。PasswordBox から取り出した文字バッファは利用直後に消去する。実カード用 PIN のバイト列は C_Login 呼び出し直後、および全ての終了経路で消去する。待機は最大60秒。Windows 資格情報の取得・保存は行わない。

## 実カード認証の実装

Program Files 内の JPKIPKCS11Auth64.dll を絶対パスで読み込み、依存 DLL の検索先をそのディレクトリと Windows の標準検索先に限定する。JPKI DLL や公式仕様書の再配布は行わない。PKCS#11 の Windows ABI は CK_ULONG が32ビット、構造体は1バイト境界。C_GetFunctionList から v2.x の関数表を取得する。

処理をプロセス内で直列化し、初期化 → カードありのスロット列挙 → 1スロットでセッション開始 → C_Login を1回 → USERCERT の取得 → 発行元・有効期限・鍵用途の検証 → ランダム32バイトの SHA-256 DigestInfo に CKM_RSA_PKCS で署名 → 証明書公開鍵で検証 → ログアウト・セッション終了・ライブラリ終了の順で実行する。PIN 照合済みという既存状態は今回の PIN 検証の代用にしない。複数のスロットにカードがある場合は PIN を送らない。

信頼の起点は公式の利用者証明用認証局の2019年・2023年の公開証明書に固定する。公式の SHA-256 指紋で検証し、Windows 全体の証明書ストアへ登録しない。チェーン検証のダウンロードを無効化し、失効は確認しない。実行中にネットワークへ利用者証明書を送信しない。成功結果は PIN とカード内秘密鍵の所持のローカル確認であり、失効済みでないことや特定の登録者との一致を保証しない。

戻り値には状態と、失敗時の処理名の列挙値・数値エラーコードだけを含め、PIN、証明書、署名、シリアルを含めない。デスクトップアプリはその固定情報と UTC 時刻のみを直近1件の診断ログに記録する。任意の文字列や例外本文はログ API に渡せない。個人に結びつくデータをファイル・ログ・テレメトリーへ出力しない。証明書と署名のバッファは検証後に消去する。アプリ自身のダンプ機能も設けないが、OS や外部ライブラリ、デバッガーの記録は別の管理範囲。キャンセルはネイティブ関数呼び出し間で確認する。実行中の関数を強制終了しないため、ドライバー応答が遅れた場合は60秒を超えることがある。

自動検証は合成鍵・合成証明書のみ。実環境では公式ライブラリのロード・初期化・PIN なしのスロット列挙、カード情報確認、セッション開始まで確認した。その後、所有者から実物カードでの認証成功の報告を受けている。開発ツールから実 PIN を扱う試験は行わない。

セッション開始前に公式シーケンスの C_GetSlotInfo と C_GetTokenInfo を呼び、カード情報を初期化・確認する。取得する一時バッファは直後に消去し、内容は表示・保存しない。接続エラーの調査では Windows の SCARD_W_REMOVED_CARD と JPKI の CKR_TOKEN_NOT_RECOGNIZED を再現し、USB 再接続とカード再提示後に PIN なしの接続・セッション開始の成功を確認した。電波環境・物理接続・ドライバー状態のどれが原因かまでは断定しない。

## 認証対象

利用するのは利用者証明用電子証明書。署名用電子証明書、券面事項入力補助 AP、個人番号の読み取りは利用しない。4桁 PIN の確認だけでなく、その秘密鍵で新しいランダムチャレンジに応答できることを検証する。登録は既存の Windows 認証で本人を確認してから行い、公開鍵と Windows SID を保護された領域で結びつける。カードとスマホの証明書は別々に登録・失効できる設計とする。

Core は模擬署名検証に使用する。実カードモードは別の Jpki プロジェクトで処理し、カードから取得した公開鍵をその場で使用する。特定の所有者との対応を記録する登録ストアはまだない。いずれの成功結果も Windows ログオンの許可として使用できない。

セッションは単一呼び出し元が所有し、非同期認証を await してから Dispose する。アダプターは渡された PIN／チャレンジを変更・保存・ログ出力せず、キャンセルを尊重する。アダプターが秘密情報を複製する場合、そのコピーの消去も実装側の責任になる。

## Windows 側

Windows 統合の実装を追加済み。ネイティブの V2 Credential Provider、カード認証専用の .NET 子プロセス、カードと Windows SID の登録、DPAPI と SYSTEM／管理者限定 ACL による Windows パスワードの保護、導入・削除スクリプトを用意した。以下の段落は初期検討時の背景で、現在の採用方式と導入手順・検証限界は [Windows ログイン手順](windows-logon.md) を参照する。実際のログイン画面への登録には所有者による資格情報入力と復旧確認が必要で、ビルド・部品検証済みであることを実ログオン成功とは扱わない。

V2 Credential Provider の役割は認証情報の収集とシリアライズ。LSA の認証をカード署名だけで置き換えられるわけではない。Microsoft アカウントで使える Windows 資格情報との橋渡しは未決定。Windows パスワードを保存する方式を採用する場合は、保存・復号権限、パスワード変更、Microsoft アカウントのパスワードレス設定、オフライン状態での挙動を先に検証する。README や設定 JSON への平文保存はしない。

ログオン UI の DLL 内で .NET ランタイムやカード SDK を直接動かす構成は障害の影響が大きいため、小さなネイティブ Provider と別プロセスの C# サービスを候補とする。サービスを設ける場合は呼び出し元 SID、セッション、要求の一意性、期限、応答の完全性を検証する。任意のプロセスに Windows 資格情報を返す API を作らない。

標準のパスワード／Windows Hello Provider は残す。Credential Provider Filter による他方式の非表示は行わない。専用ローカル管理者から復旧できることを検証後、まず VM で導入・削除・再起動・ロック解除・サービス停止・SDK 例外の試験を行う。

## Android

その後、所有者から Android の PIN 照合・署名検証にも成功したとの報告を受けた。現在の初期モードは自動判別。公開の種類名が実物カードなら PC/SC の検出用接続をリセット・解放してから既存の PKCS#11 経路を開き、Android なら検出した NFC 接続をそのまま使用する。判別前に PIN を送信しない。未知の種類は拒否し、PIN 誤りや認証失敗を理由に別経路へ切り替えて再送しない。PIN 入力 → 提示という操作順を維持するため、利用者は提示する媒体に対応する PIN を入力する。カード用・スマホ用 PIN の両方を試す機能は設けない。

所有者の希望により、RC-S300 に S25 をかざし、PC にスマホ用 PIN を入力する試験経路を実装した。生体認証による PIN の省略は行わない。スマホのロック解除と、JPKI の利用者証明用 PIN の照合を区別する。

実物カード用 JPKIPKCS11Auth64.dll は GetTokenInfo で Android を拒否したため、Android のみ PC/SC による APDU の専用経路に分ける。物理カードモードの接続経路は変えない。選択するアプリは公開実装で示される JPKI アプリで、EF 0006 の最初の32バイトが Android の固定の種類名であることを確認する。未知の種類には PIN を送信しない。種類名以外のトークン情報、マイナンバー、署名用証明書は読まない。

PIN 照合は EF 0018 の VERIFY を1回だけ行う。証明書は EF 000A、鍵は EF 0017 を使用する。署名は既存の SHA-256 DigestInfo に対する RSA PKCS#1 v1.5 とし、端末の応答が 61xx の場合は GET RESPONSE だけを続け、VERIFY／SIGN 自体は繰り返さない。処理後は PC/SC のトランザクションと接続をリセット・解放する。PIN 用の送信配列と応答・証明書・署名の配列は消去する。

参考にしたプロトコルの一次資料は [myna-card 3.3.4 の公開実装](https://docs.rs/crate/myna-card/3.3.4/source/src/ap/jpki.rs)。コードを組み込み・再配布しておらず、C# の実装とテストは独立して作成した。メーカーの保証された SDK への対応ではないため、Android 経路は試験扱い。

実機では S25 の JPKI アプリ選択と Android の種類確認に成功した。PIN 前の証明書読み取りは 6982（条件未充足）で拒否されたため、証明書は PIN 照合後に読む。実機で PIN を送信した検証は開発ツールから行わず、合成の応答で PIN の一度限りの送信・消去・証明書検証・署名検証・応答連結を確認している。実際の Android 認証の成功は所有者の操作で確認する必要がある。

対象機器は RC-S300 と Galaxy S25。RC-S300 は実物マイナンバーカードへの対応をソニーが明示している。Windows では NFC ポートソフトウェアの導入が必要。PC/SC リーダー列挙の診断を追加したが、リーダー名は型番・ファームウェア・スマホ対応の証明にはならない。

RC-S300/S1 はソニーがスマホのマイナ保険証への対応を明示する業務用途モデル。個人向け RC-S300 と同じ対応範囲とは判断しない。医療用サービスへの対応は独自 Windows ログオンで SDK を利用できる証明でもない。まず実物カードを対象にし、スマホ搭載証明書の直接読み取りは本体のモデルと SDK の対応を別途確認する。

Galaxy S25 は国内版／海外版、型番、OS、電子証明書の搭載状態を実機で確認する。JPKI の NFC 読み取り対応一覧への掲載だけで、スマホ搭載証明書の外部リーダーからの利用を保証しない。

Android の搭載電子証明書は物理カードと同一ではない。スマホを物理カード読み取り用リーダーとして使う機能とも区別する。端末、搭載サービスの世代、リーダー、SDK の対応範囲を実機で確認する。

PC で PIN 入力 → スマホ提示という希望の操作が可能かは SDK 次第。デジタル認証サービスとスマホアプリ経由の方式も候補だが、利用申請・ネットワーク・別端末連携が必要となるため、個人のローカル Windows ログオンで利用可能かを確認する必要がある。未対応の方式は成功扱いにしない。
